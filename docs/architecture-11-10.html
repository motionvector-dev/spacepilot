Phase 1

Event-Driven State (Replacing MongoDB Polling)

Currently, the Node backend, DO Orchestrator, and local workers rely on high-frequency polling against MongoDB (find_one_and_update and heartbeat timestamps) to pass the job baton. This creates race conditions, deadlocks, and fragile "staleness watchdogs."

The Upgrade: Introduce a true message broker (e.g., AWS SQS or Redis Streams). The backend drops a job onto an upscale-jobs queue. Workers pull from the queue, locking the message via a visibility timeout. If a worker crashes, the timeout expires, and the message is instantly re-queued with exactly-once delivery guarantees.

Phase 2

Unified Inference Runtime (ONNX)

Currently, the Mac worker completely rips out the core torchaudio/h264_cuvid/TensorRT engine and replaces it with CoreML and VideoToolbox. Maintaining separate execution paths inevitably invites visual drift (FP16 rounding errors, color space shifts).

The Upgrade: Stop maintaining two separate inference stacks. Compile the PyTorch models (srvgg_leaky_relu) into ONNX or Apache TVM. ONNX Runtime executes the exact same graph via the CoreML Execution Provider on the Mac, and the TensorRT Execution Provider on the 5090/Runpod, guaranteeing true mathematical equivalence.

Phase 3

Virtual Fleet Abstraction (Unified Scheduler)

Currently, the Node backend explicitly codes routing logic for specific hardware (e.g., < 60s -> Mac, > 1800s -> Runpod). Adding new hardware (like AMD MI300s) requires rewriting backend business logic.

The Upgrade: Extract dispatch into an independent Scheduler Service. The backend submits a job statelessly. The Scheduler maintains a live inventory of connected nodes via WebSockets, evaluates real-time capacity and cost margins, and routes the job to the optimal tier automatically.

Phase 4

Distributed Tracing (OpenTelemetry)

Flattening pod errors into a Mongo string field (from PR #9) was a vital stopgap, but SSH-ing into a Mac to read worker.log or grepping Mongo is not a hyperscale debugging strategy.

The Upgrade: Instrument every stage (preprocess, gpu, postprocess) with OpenTelemetry (OTel). Pipe logs, VRAM metrics, network I/O, and trace spans to a centralized dashboard (Datadog or Honeycomb). When a job fails, you instantly see a visual waterfall chart of exactly which pod, host, and ffmpeg subprocess failed, alongside its hardware metrics.

Phase 5

Pull-Based Fleet Deployments (NixOS / Ansible)

Pushing code to the Macs currently requires running a manual deploy.sh script over SSH from a specific laptop. This creates a bottleneck and makes emergency rollbacks dangerous.

The Upgrade: Use a pull-based configuration manager. The Macs and the 5090 run an agent that listens to the main branch. When a PR merges, the local boxes automatically pull the code, rebuild their virtual environments, gracefully drain their current jobs, restart the worker process, and reconnect to the load balancer. True zero-downtime, hands-free continuous deployment.
